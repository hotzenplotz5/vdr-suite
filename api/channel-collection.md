## Status and source of truth

The read-only `GET /api/v1/channels` contract was accepted in Phase 69.D (PR #364); the independent JavaScript consumer was accepted in Phase 69.F (PR #377). This page is reconciled against the source in `main` at `8d8dcfbf26d0b6760ad81dc4b2af4fbbd15d55b0` (2026-10-11). It documents source behavior, **not** the installed daemon binary or VIDAA hardware acceptance.

## Request

```http
GET /api/v1/channels?backendId=backend-a&backendId=backend-b&limit=50&sort=backendId,channelId&order=asc
```

- `backendId` is **required** 1–16 times as repeated URL query keys. No implicit default backend, wildcard or automatic all-backends request exists. Each backend ID is distinct, 1–128 characters from letters, numbers, dot, hyphen or underscore.
- `limit` is optional, 1–100, default 50; `cursor` is optional, nonempty and opaque (at most 4096 characters).
- `sort` accepts only `backendId,channelId`, `order` accepts only `asc`. Unknown or repeated non-`backendId` query fields, unsupported values, or duplicate backend IDs are invalid.
- **Do not copy** the unversioned `/api/vdr/channels` or browser-only route behavior; the public-v1 shape is intentionally different.

## Authentication and authorization

A valid authenticated actor is required, with the `channels.view` permission **for every selected backend**. The security gate checks each source separately. One unauthorized backend rejects the **entire request**, normally with 403; unauthorized source names are not leaked through `meta.sources`. Missing or invalid backend scopes return 400, absent authentication returns 401.

The concrete credential transport is owned by the deployment's identity/security contracts and is not invented by this OpenAPI subset. Clients should supply supported caller-owned authorization, using `getChannels({query:{backendIds:[...]}})` in the [reference JavaScript client](../clients/reference-js/public-v1-client.js).

## Response and identities

The public Channel ID is the **pair `(backendId, channelId)`**; channel number and display fields are mutable attributes. A Channel row contains exactly `backendId`, `channelId`, `channelNumber`, `name`, `provider`, `groupName`, `radio`, `encrypted` and `enabled`. Backend hostnames, transport details, native paths or adapter URLs are not exposed.

Illustrative partial-success response (server shapes confirmed in `PublicApiRuntime.cpp`):

```json
{
  "items": [
    {
      "backendId": "backend-a",
      "channelId": "S19.2E-1-1019-10301",
      "channelNumber": 1,
      "name": "Channel One",
      "provider": "provider",
      "groupName": "group",
      "radio": false,
      "encrypted": false,
      "enabled": true
    }
  ],
  "page": {"limit": 50, "nextCursor": null, "hasMore": false},
  "meta": {
    "partial": true,
    "sources": [
      {"backendId": "backend-a", "state": "ok"},
      {"backendId": "backend-b", "state": "unavailable", "code": "backend_unavailable"}
    ]
  },
  "links": {
    "self": "/api/v1/channels?backendId=backend-a&backendId=backend-b&limit=50&sort=backendId,channelId&order=asc",
    "next": null
  }
}
```

**HTTP 200 with `meta.partial=true` is not a fully successful read from all backends.** The caller must display or otherwise account for unavailable sources. One available but empty Channel snapshot still counts as an `ok` source. If every selected source is unavailable, the response is `503 backend_unavailable`, not a fabricated empty 200.

The response uses `Cache-Control: no-store` and **no collection ETag**.

## Keyset pagination

Items use `backendId ASC, channelId ASC`; the source order in the query is normalized. Start with all explicitly selected backend IDs, read `page.hasMore`, then follow the exact `links.next` URL or pass the returned `page.nextCursor` **with the same source set**. The current `ch1_` cursor format is internal and must not be decoded or generated by clients.

A `409 cursor_expired` means the requested backend scope changed: throw away the old cursor and start again with the first page. Pagination is not a frozen snapshot, and no retry should silently switch to legacy routes.

## Channel numbering versus the current collection order — Samsung hardware finding (2026-10-25)

**Verified current wire behavior:** the original collection sorts by `backendId ASC, channelId ASC`. The `channelNumber` field is delivered as a display attribute, **not** an ordering key. The Samsung S3.3 client currently requests `sort=backendId,channelId&order=asc` with `limit=20`; therefore an initial page can contain widely separated native channel positions (for example 1, 17 and 230). This is contract-compliant but **does not satisfy the product requirement** to list channels in VDR `channels.conf` order.

**Required follow-up, not yet implemented or accepted:** introduce a reviewed, explicitly requested public-v1 numeric-order collection mode for channels of one backend (or a well-defined backend-first composite for federation), ordered by **native `channelNumber ASC`, with stable `channelId` tie-break**. Document the precise request, cursor semantics, channel snapshot/reordering policy and error cases before changing the wire contract. Existing `sort=backendId,channelId` and `ch1_` consumers must remain compatible. Backend-scoped `channels.view`, bounded pages, partial-source semantics and secure Device authentication must not change. Update runtime, OpenAPI, reference client, Samsung client and positive/negative contract tests together. Do **not** silently advertise a `sort=channelNumber` value or a new cursor as working until those implementations and tests exist.

Sorting **only the 20 rows in one received page** is incorrect: page 1 would still omit earlier `channels.conf` positions located on later `channelId` pages. Sorting after downloading the entire Channel catalog would defeat bounded television-client pagination. The adjacent-channel operation below is a separate CH+/CH− contract, not a substitute for a correctly paginated Channel list.

**Real Samsung evidence:** on 2026-10-25, Tizen 5.5 Samsung S3.3 displayed 20 genuine public-v1 channels from backend `default` after a separately administered `channels.view@default` grant. The same Device previously saw **no available backends** without that grant. This verifies Device authentication, permission-sensitive discovery and the first Channel page on the observed installed server; it does **not** accept the requested numeric ordering, a second cursor page, TV playback, EPG, restart persistence or any independent Hisense result. See the [single cumulative API-v1 hardware matrix](../docs/development/public-v1-final-hardware-acceptance.md).

## Additive numeric VDR-neighbor operation (October 2026 candidate)

The original Channel collection above **retains** its stable `ch1_` cursor
and `backendId ASC, channelId ASC` ordering. That listing is **not**
the native VDR tuning sequence; a paginated 30-item client view is
not an authoritative basis for CH+/CH−.

The same **authorized** Public-v1 endpoint now supports a separate, bounded
`GET` variant for one adjacent enabled, nonradio TV channel:

```http
GET /api/v1/channels?backendId=home&limit=1&relativeTo=S19.2E-1-1019-10301&direction=up
```

The request must supply exactly one explicitly authorized `backendId`,
one native public `channelId` in `relativeTo`, `direction=up|down`,
and `limit=1`. `cursor`, `sort`, and `order` are forbidden.
The existing SecurityHttpGate still enforces `channels.view@backend`;
Device credentials are not bypassed. The daemon uses the complete current
VDR snapshot, ascending `channelNumber` (stable `channelId` tie-break),
with first/last wrap and disabled/radio channel exclusion. The response
uses the usual single-item `items` list and `page.hasMore=false`,
`page.nextCursor=null`, `meta.partial=false`; unknown current channel,
noneligible current channel, or no second eligible channel returns
`404`. The variant does not create or stop a media session.
All playback remains within the separate authorized Device MediaSession
contract and one client playback owner.

Provenance warning: this is a *development-branch source candidate*,
not confirmation that any running yaVDR daemon serves this new variant.
The established Hisense Live-TV playback continues to work independently.
Relevant regression targets: `test-phase69d-public-channel-collection`,
`tools/check_phase69d_public_channel_collection.py`, and
`tools/check_public_v1_openapi.py`. The branch integration preserves
the real `/api/v1/search/recordings`, `/api/v1/search/epg`, and three
Live Device SecurityHttpGate route cases rather than suppressing their
OpenAPI drift checks.

## Errors

| HTTP | Meaning | Recommended client action |
| --- | --- | --- |
| `400` | `invalid_request` or `invalid_backend_scope`; unsupported query, missing/duplicate source or malformed cursor | Fix the caller input |
| `401` | Authentication required | Supply valid actor credentials |
| `403` | Any `channels.view@backend` denial | Remove unauthorized requests through explicit user/server policy; do not probe privately |
| `405` | `method_not_allowed`, `Allow: GET` | Use GET |
| `409` | `cursor_expired` | Restart the complete traversal |
| `503` | `backend_unavailable` when all sources fail, `service_unavailable` or security-gate failure | Show error or partial state; do not present as complete empty list |

The REST runtime emits `application/problem+json` including a stable code, request ID and optional correlation ID. Earlier security-gate rejections may have their own detail text.
