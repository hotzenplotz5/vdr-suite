# MT.I4.4 — Manual-install to Debian package adoption: observed host and offline proof

**Status (2026-11-15):** MT.I4.4 is in progress, with **only a synthetic Media Tools add-on ownership/rollback rehearsal**. A four-package production transition, real SQLite schema migration, live rollback, PPA publication, and deployment have **not** been authorized or verified. This document does not introduce a second installer or an installation approval.

## Evidence from the operator's read-only yaVDR inspection

- **Host:** Ubuntu 26.04 Resolute, amd64; VDR package `2.8.3-0yavdr0~resolute`. VDR, Suite daemon, and Backend Agent were all `active/running` during inspection. The agent runs as `vdr:vdr`.
- **Ownership:** `vdr-suite-daemon`, `vdr-suite-backend-agent`, `vdr-plugin-suitebridge`, and `vdr-suite-addon-media-tools` were absent from dpkg's installed package inventory. Their observed binaries/worker paths reported **no dpkg owner**. The existing daemon service is installed under `/usr/lib/systemd/system/` and has the operator's `recording-artwork.conf` drop-in. The agent has `20-media-tools.conf`.
- **Media Tools:** the existing manual inventory identifies source `b4727cb39b50f102da5805973a0f9b3a5c447809`, module version `0.1.0`, and package name `vdr-suite-addon-media-tools`. All **seven** inventoried payload entries matched installed bytes, modes, and SHA-256; with the inventory file itself, the canonical package payload has **eight** files. The installed import worker digest matched the inventory's approved handler digest. This proves **local inventory consistency**, not compatibility with a later published package or an independently reapproved handler.
- **State:** an active SQLite database and WAL sidecar were observed; manual approval, import source ledger, and both service overrides exist. `rectools.import-running.lock` was an empty root-owned 0644 regular file, link count 1. `lslocks` showed no current lock at that instant; this is **not** a maintenance lock held by the migration operator and does not prove the operation queue is drained.
- **Package source:** `apt-cache policy` found no candidates for the four Suite packages in the current host configuration. No configured `hotzenplotz5/vdr-suite` PPA entry was found by the read-only source scan; this **does not** establish whether package versions are available remotely.
- **Local source tree:** `/home/yavdr/vdr-suite` was on `main` at `88d220107f34af4cc692dca830992af6a5cbc7dd`, with three untracked paths. GitHub `main` was ahead; no fast-forward, cleanup, local build, or host modification was performed.

These are dated observations and must not be promoted to continuing health or current source-version assertions. Do not disclose approval contents, credentials, customer recordings, SQLite records, or embedded host URLs.

## MT.I4.4 staged implementation and acceptance boundaries

1. **MT.I4.4a — synthetic add-on ownership handover / rollback (first proof).** Extend the *existing* `tools/addons/test_debian_media_tools_lifecycle.py` instead of adding an installer. Build the already supported sealed-stage fixture package in a disposable root with isolated dpkg database. Materialize all eight original manual-file fixtures; verify that the package's real preinst **refuses** direct takeover without changing the bytes. Then simulate a previously reviewed operator transition on those fixture files only, install the package through that isolated dpkg, preserve independent configuration/approvals/source ledger/SQLite+WAL+SHM/video/nginx/overrides, purge the package, and restore every manual file with exact prior bytes and modes. Verify package status after adoption. No installation, delete, or lock acquisition on `/` occurs. **This proves only a synthetic add-on rollback; it is not the procedure to run on yaVDR.**
**MT.I4.4a supplementary fixture — present host remains untouched:** Existing `tools/test_packaging_p8_installer.py` now reconstructs the observed manually installed **four-component** yaVDR file layout in a private directory, including both units and drop-ins, the optional add-on inventory, persistent lock, operator nginx, approval, source ledger, SQLite and WAL sentinels. Its `--check` readback verifies unowned core package targets and legacy SuiteBridge ABI; `--install` must refuse the whole migration without changing any sentinel bytes. This negative proof does **not** complete the positive full four-package transition in MT.I4.4b.

2. **MT.I4.4b — all four package owners.** Extend an isolated fixture to cover daemon, backend agent, SuiteBridge, and the optional add-on *together*, including the P8 `/usr/share/vdr-suite` known co-owner fix, nginx snippet, systemd unit and manual `/usr/local` variants. Demonstrate concrete preserved-state behavior under install, upgrade failure, remove and recovery using actual target-architecture binaries. Existing MT.I4.3 clean-host co-installation (CI [43755920343](https://github.com/hotzenplotz5/vdr-suite/actions/runs/43755920343)) is **not** this prior-manual-install adoption test.
3. **MT.I4.4c — data/service recovery contract.** Establish the supported manual predecessor's executable and schema provenance, identify active writers and uncompleted operations, and separately test a **consistent** quiesced SQLite snapshot including WAL effects and restore. Audit service stop/start order, `User=vdr` agent, root-run daemon, effective drop-ins, nginx includes, plugin ABI, and trusted credentials without copying sensitive content into fixture output. Identify a verified recovery path to the old *complete* runtime and service state. Do not derive DB backup from an uncontrolled live `.db` copy.
4. **MT.I4.4d — explicit release and operator decision.** Select a published, verified **exact** Resolute four-package source/version and dependency/ABI path, validate in a disposable release-equivalent environment, and document a specific maintenance and rollback sequence. Launchpad publishing, production takeover, permission changes, service changes, and activation remain distinct actions requiring the maintainer's explicit approval; none follows automatically from a green fixture or CI.

## Current decision

- The current manual VDR-Suite remains installed, running, and untouched.
- **Do not** `apt install`, `dpkg -i`, `apt purge`, delete any manual payload or lock file, change approvals/configuration, or stop services on the live yaVDR as an MT.I4.4 test.
- Do not confuse an empty, persistent `rectools.import-running.lock` with evidence of a safely held exclusive maintenance lock.
- Existing real blockers include unowned package target files, a running SQLite/WAL workload, operator-managed systemd/nginx configuration, unverified all-component manual predecessor compatibility, and the absent configured Suite PPA candidate.
- Existing `tools/packaging_p8_installer.py --install` intentionally has **no live migration implementation**. This slice does not change that behavior. The historical [P8 manual-adoption evidence](packaging-p8-yavdr-adoption-boundary.md) remains applicable, updated only by new dated observations.
