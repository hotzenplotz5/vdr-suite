# P8 — fail-closed installation entry point (unreleased)

Status: **pre-install gate implemented; no host installation authorized**.
The P6/P8 drop-in regressions and an actual daemon `dpkg --unpack`
unowned-nginx collision refusal were verified in
[CI #109](https://github.com/hotzenplotz5/vdr-suite/actions/runs/38926400765), all six jobs SUCCESS, exact code
SHA `643166983f961bcf450d9c785cf1e628dc31d684`. The disposable test confirmed unchanged snippet SHA-256
and no unpacked daemon executable; this is not a live-host acceptance.

## Source of truth

The only new P8 command entry point is
`tools/packaging_p8_installer.py`. It imports and runs
`tools/packaging_host_collision_preflight.py` directly; it does not copy the
P6 destination/ownership/nginx scanning logic or create a second package
builder. Existing package manifests in `debian/*.install`,
`debian/rules` and staging in `mk/install.mk` remain authoritative.

For a **read-only** inspection of the actual host, from the verified source
checkout as an ordinary user (no sudo):

```sh
python3 tools/packaging_p8_installer.py --check
```

For offline unit tests, `--root` points to an isolated fixture. This is
not a way to bypass the installation gate.

## Enforcement boundary

`--install` always evaluates the P6 inspection first and **always refuses**
the operation, including when the scanner returns `NO_KNOWN_CONFLICT`.
The JSON outcome contains `decision: BLOCKED`,
`install_approved: false`, the actual P6 verdict and public finding codes,
but no config contents or secrets. The command returns status 3. A scanner
error returns status 2 and performs no writes. It never invokes `apt`,
`dpkg`, `make install`, a service manager, nginx or a runtime deploy.
`--check` also fails closed on process status: 2 for `BLOCKED`,
3 for `REVIEW_REQUIRED` or `NO_KNOWN_CONFLICT`, because no P8
installation policy has been approved. This intentionally differs from
the standalone P6 diagnostic command (which returns 0 for non-blocking
review results). Do not use a successful diagnostic run as an installation
authorization.

The planned `--build` and `--uninstall` options are reserved and also
refuse execution (status 3); the existing independent package build/staging
flows are unchanged. Do not add a competing package builder.

**The P8 entry point is still not a release or migration installer.**
A separate, narrowly scoped *package-native pre-unpack collision guard* is now
generated by `tools/packaging_p8_preinst.py` from the three canonical
`debian/*.install` manifests. During `debian/rules`,
`override_dh_installdeb` stages POSIX-shell `preinst` scripts into each
built package's `DEBIAN` metadata, including plugin-only builds. At dpkg
install/upgrade time (before package contents are unpacked), the guards refuse
unowned/foreign-owned manifest targets, target symlinks/special files,
manifest directory roots such as `/usr/share/vdr-suite`, compressed manual-page
candidates, and SuiteBridge ABI wildcard paths. They also refuse known
unmanaged `/usr/local` binaries and systemd overrides. Existing
operator-managed systemd drop-in directories also block a first daemon/agent
package installation, but do not automatically block upgrades of
packages that already own their own target files. Existing
`/var/lib/vdr-suite` blocks a *first* daemon/agent package installation;
an already package-managed upgrade does not automatically fail merely because
the package-managed service maintains state there.

The generated script uses only `/bin/sh` and `dpkg-query` on the target; it
does not require the P6 Python program to have been installed first. Abort
and recovery dpkg maintainer-script actions remain unblocked. The generator is
the shared manifest source; **there is no parallel hard-coded installer
file inventory**.

**Limit:** The package-native guard prevents its enumerated collision cases
during ordinary dpkg execution, but is **not the full P6 scan, a P7 schema
compatibility policy, a service-/nginx-route parser, or an installation
authorization**. A same-package-owned target is not evidence that a running
database is upgrade-compatible. The P8 `--install` entry point still always
refuses installation. Direct `apt`/`dpkg` cannot be treated as a supported
host deployment route until a documented mandatory authorization/transition
gate covers source version, runtime state, nginx, database and service policy.
No productive yaVDR package install is authorized by adding this script.

## Required next P8 work

1. Establish an explicit per-path takeover policy, package-specific
   ownership/upgrade policy and VDR ABI/service compatibility matrix.
2. Verify the expanded six-scenario disposable `dpkg --unpack`
   collision matrix: daemon nginx snippet, systemd drop-in and existing state;
   Backend Agent configuration and systemd drop-in; SuiteBridge ABI file.
   Each isolated case must prove the expected preinst refusal, unchanged
   sentinel bytes and absence of unpacked payload. The original nginx-only
   scenario was verified in CI #109; additional scenarios remain pending
   the exact new-head CI result. Expand the direct-package gate to remaining
   protected installation/upgrade conditions before host authorization.
   A `postinst` cannot protect files already replaced during unpack.
3. Determine the actual active systemd daemon binary, nginx route/include
   topology and older source/database provenance. Do not replace operator
   managed `/etc/nginx`, `/etc/default`, `/etc/vdr-suite` or `/usr/local`
   on the strength of a successful scanner run.
4. Preserve the P7 no-live-migration requirement and obtain separate
   authorization for service/DB operations. Only then implement guarded
   package installation and lifecycle acceptance.

Regressions:
`python3 -m unittest discover -s tools -p 'test_packaging_p8_installer.py'`
and `python3 -m unittest discover -s tools -p 'test_packaging_p8_preinst.py'`
use private temporary directory trees only. The existing P6 scanner
regressions remain required. Package-build and disposable dpkg integration
remain CI gates; this is not productive installer acceptance.
