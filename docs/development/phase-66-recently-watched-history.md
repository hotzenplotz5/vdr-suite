# Phase 66.6 — Recently Watched / History

Status: **AUTHORIZED / ACTIVE**

This document records the bounded runtime contract for Slice 66.6. It complements the Phase-66 plan and ADR-0058; it does not authorize Slice 66.7 or later work.

## Purpose

Recently Watched is a durable, actor-scoped projection of accepted Recording playback activity. It is intentionally distinct from Continue Watching:

- **Continue Watching** answers which Recording currently has truthful resumable state.
- **Recently Watched** answers which supported Recording was recently observed through the canonical playback owner, including completed playback where that completion is known.

A Recording may therefore disappear from Continue Watching after completion and remain in Recently Watched.

## Supported content identity

Slice 66.6 supports existing VDR Recording identity only:

```text
(backend_id, recording_id)
```

`recording_id` is the existing canonical Recording identity. `backend_id` preserves existing backend scope. No second Recording identity, Home catalog, content graph or provider-native identifier becomes authoritative.

Rows whose Recording can no longer be resolved through the existing `VdrRecordingCacheRepository` are not exposed and are pruned when encountered.

## Actor scope and privacy

History state is keyed by:

```text
(actor_id, backend_id, recording_id)
```

The actor is taken from the existing trusted request/security context. Clients do not submit or select another actor in the History payload.

`POST /api/media/recently-watched` reuses the already accepted Recording MediaSession authorization/CSRF boundary (`/api/media/sessions`, `media.recording.play`). Requests are same-origin and responses are `Cache-Control: no-store`.

There is no cross-actor list operation and no browser-local global History authority.

## Source of evidence

The only accepted activity evidence in this slice is:

```text
canonical-recording-playback-owner
```

The browser integration observes the already canonical Recording playback owner through its existing `snapshot()/subscribe()` lifecycle plus normalized owner capabilities such as position and resume support. It does not infer global History from Home DOM state, card clicks, route selection, `localStorage`, hidden media elements or a second player/session owner.

An actual media `ended` event observed inside the canonical owner supplies explicit completion evidence. It does not create an independent playback lifecycle.

The evidence name is assigned server-side. The API does not accept arbitrary client-provided evidence authority.

## Persistence model

History is deliberately **not an event log**. The durable table stores at most one current History activity record for each actor/backend/Recording tuple:

```text
actor_id
backend_id
recording_id
position_seconds
position_known
completion_known
completed
resume_relevance_known
resume_relevant
source_evidence
last_activity_at
last_operation_id
```

A newer accepted activity upserts the tuple and advances its server timestamp. Replaying the same `operation_id` is idempotent and does not advance ordering or overwrite state.

This model preserves the minimum truth needed by the product rail without creating analytics, viewing telemetry history, a recommendation authority or a knowledge graph.

## Activity ordering

`last_activity_at` is generated by the server database when activity is accepted. Recently Watched is returned in descending `last_activity_at` order with Recording identity as the deterministic tie-breaker.

Browser wall-clock timestamps are not accepted as ordering authority.

## Completion and resume relevance

Completion and resume relevance remain explicit tri-state-style truth through `*_known` flags:

- `ended=true` from the canonical owner makes completion known and completed.
- Otherwise, when canonical current Recording duration and owner position are both known, completion is derived by exact position/duration comparison.
- Unknown duration does not fabricate completion.
- A known completed item has known `resume_relevant=false`.
- For a non-completed item, resume relevance is only marked known when the canonical owner reported whether resume is supported.
- Position may be unknown; unknown position is not converted into a fabricated zero-position viewing claim.

Recently Watched does not copy Continue Watching state and Continue Watching is not treated as an event log.

## Retention and pruning

History is bounded to the **100 most recent Recording identities per actor/backend**.

Pruning occurs on accepted writes. The oldest rows by server activity ordering are removed once the bound is exceeded. This prevents the Slice-66.6 store from silently becoming long-term analytics/event storage.

No time-based retention or recommendation weighting is introduced by this slice.

## Update semantics and failure isolation

Canonical owner activity is recorded independently of Continue Watching mutations. The browser uses separate mutation queues for the two semantics so a History failure cannot reorder or poison Continue Watching state, and vice versa.

The owner is sampled only while canonical playback is active. A final accepted observation is attempted when an observed active lifecycle becomes inactive; explicit `ended` records completion. Duplicate operation replay is safe.

History API/read failures fail closed for the History rail: the rail is omitted/cleared while ordinary Home browsing, Recording discovery and playback ownership remain available.

## Home projection

The Home section is a projection only. It:

- lists actor/backend-scoped server History;
- uses existing Recording title, metadata and preferred artwork truth;
- displays completion/resume relevance only when known;
- opens the existing Recordings2 detail/playback surface;
- releases Deferred Live Preview before explicit ownership transfer;
- does not auto-start or invent a History-specific resume decision.

The section is composed after the existing Recording Discovery runtime and reuses its established rail/card presentation classes. It creates no second navigation owner.

## Explicit non-goals

Slice 66.6 does **not** introduce:

- recommendations or personalized rail ranking;
- a watch-event analytics log;
- Phase-70 content knowledge graph work;
- a second Recording identity or content catalog;
- a second playback/session owner;
- provider-native playback authority;
- Live-TV watch history;
- browser-local cross-client truth;
- Slice 66.7 or later Phase-66 behavior.

## Verification surfaces

Repository tests must prove at minimum:

- actor/backend isolation;
- Recording identity validation;
- completed content remains valid History state;
- Continue Watching and History semantics can differ;
- unknown completion/resume facts remain unknown;
- activity ordering is server-owned;
- duplicate operation replay is idempotent;
- retention is bounded to 100 rows per actor/backend;
- deleted/missing Recording truth is not exposed;
- production frontend composition loads the History rail;
- canonical playback-owner lifecycle is the activity source;
- existing Recording playback flow remains the only explicit playback owner;
- authorization/CSRF and packaging/install wiring are preserved.

A real yaVDR/browser acceptance block is only valid for an exact-head candidate after the relevant hosted CI gates are green.
