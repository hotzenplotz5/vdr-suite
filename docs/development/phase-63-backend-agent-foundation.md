# Phase 63 Slice 1 — Backend Agent Enrollment and Lease Foundation

## Status

Implementation slice in progress on `agent/phase63-backend-agent-foundation`.

This document is the binding contract for the first Phase-63 runtime slice. It narrows ADR-0039 through ADR-0043, ADR-0048 and ADR-0049 to one read-only lifecycle path. Target architecture not named as implemented here remains future work.

## Slice goal

Provide a persistent Control-Plane foundation for one explicitly enrolled Backend Agent to authenticate for one Backend, negotiate one supported Agent protocol version, receive one current backend generation, publish a bounded read-only capability set, renew a lease through monotone heartbeats and reconnect without allowing an obsolete or revoked Agent instance to become authoritative.

The first slice executes no VDR operation and introduces no public provider URL.

## Included

- persistent Agent identity and Backend binding;
- controlled, idempotent enrollment using an administrator-authorized one-time enrollment identity;
- separation of enrollment identity from the resulting runtime credential reference;
- fenced Agent-initiated runtime credential rotation with restart-safe lost-response recovery;
- replacement enrollment for a Backend after the previous Agent identity is revoked while retaining history;
- a local accountable status/revocation utility that exposes no Agent secret material;
- Agent software and Agent protocol version validation;
- one monotonically increasing `backendGeneration` for each newly accepted runtime instance;
- authenticated Agent-originated protocol requests;
- monotone heartbeat sequence and deterministic lease renewal;
- derived `online`, `stale`, `offline`, `revoked` and `incompatible` presentation states;
- bounded read-only capability publication and revision;
- reconnect reconciliation for identity, binding, generation, heartbeat sequence and capability revision;
- append-only accountability evidence for enrollment and protected lifecycle transitions;
- SQLite persistence, migration, restart recovery and backend isolation.

## Explicitly excluded

- Timer, Recording, SearchTimer, Remote, configuration or provider mutations;
- command inbox, result outbox, operations, jobs or execution retries;
- snapshot or change-feed ingestion;
- provider selection or provider credential exchange;
- Streaming Gateway, OSD bridge or any Phase-64-or-later work;
- public RESTfulAPI, SVDRP, SuiteBridge, Streamdev or plugin URLs;
- browser delivery of Agent credentials, credential references or secret-bearing diagnostics;
- automatic write enablement after enrollment;
- changing existing `BackendNode.online` or direct-adapter availability before a later explicit provider/ownership selection slice;
- a second BackendRegistry, security service, accountability store or job system.

## Identity and sequencing axes

These values are independent and must never be silently reused as each other:

| Value | Meaning | Lifetime / ordering |
| --- | --- | --- |
| `AgentId` | Stable Suite-owned identity of the enrolled Agent device | Stable across process restarts and credential rotation |
| `BackendId` | Stable Suite-owned backend/site identity | Existing BackendRegistry authority |
| `EnrollmentId` | Stable identity of one controlled bootstrap request | One enrollment purpose; terminal after use or revocation |
| `CredentialGeneration` | Generation of the Agent runtime credential reference | Increments on rotation; old generations fail closed |
| `AgentInstanceId` | Identifier generated for one concrete Agent process start | New for every process instance |
| `backendGeneration` | Control-Plane fencing generation for one accepted Agent instance | Strictly increases per Backend on accepted takeover |
| `agentProtocolVersion` | Version of the machine protocol contract | Compatibility axis, not a resource revision |
| `heartbeatSequence` | Monotone sequence inside one accepted backend generation | Starts at one; duplicate is idempotent; lower values are stale |
| `capabilityRevision` | Monotone revision of capability facts inside one accepted generation | Independent from heartbeat sequence |
| future `snapshotGeneration` / `snapshotRevision` | Ownership/revision of a future observed snapshot | Not implemented by this slice |
| future `CommandId` / `OperationId` | Durable future mutation identities | Not implemented by this slice |

## Domain values

### `AgentId`

- opaque Suite-owned text identifier;
- non-empty, bounded to 128 bytes;
- no embedded secret or Backend inference;
- generated by the Control Plane, never trusted solely from request input.

### Enrollment identity

An enrollment record binds:

- `EnrollmentId`;
- target `BackendId` from administrator-authorized Control-Plane state;
- enrollment-token verifier or existing managed credential reference;
- creation and expiry timestamps;
- persisted status: `pending`, `consumed` or `revoked`; expiry is authoritative from `expiresAt` and is treated as an effective terminal `expired` state during consumption;
- resulting `AgentId` after successful consumption;
- accountability correlation.

The raw bootstrap secret is never persisted or logged. Enrollment is idempotent only for the same valid enrollment identity, Backend binding and resulting Agent identity. Reuse with conflicting data fails closed.

### Backend binding

One active Agent identity belongs to exactly one Backend in this slice. A Backend may retain revoked historical Agent identities, but a partial uniqueness constraint permits at most one non-revoked Agent binding at a time. A request-supplied Backend ID is only a claimed routing value. Authority comes from the persisted Agent binding plus the existing BackendRegistry record. Enrollment and lease state do not overwrite the existing direct-adapter `BackendNode.online` flag; provider/ownership selection is a later bounded slice.

### Protocol compatibility

The first runtime protocol accepts exactly `vdr-suite-agent/1`. A request with any other version is recorded as incompatible and receives no generation or lease. A future compatible range requires an explicit protocol contract. Agent software version is descriptive and bounded; it is not authorization.

### Backend generation

`backendGeneration` is allocated by the Control Plane in the same transaction that accepts a new `AgentInstanceId`. Repeating the same connect request for the current Agent instance is idempotent and returns the same generation. A distinct accepted instance increments the Backend generation and fences the former instance immediately.

### Heartbeat and lease

A heartbeat contains the persisted Agent identity established by authentication, the claimed Backend ID, current backend generation, Agent instance ID, protocol version and `heartbeatSequence`.

Rules:

- sequence `1` is the first accepted heartbeat for a generation;
- the current sequence plus one advances the lease;
- an exact duplicate is idempotent and does not create a second transition;
- a lower sequence is stale and rejected;
- a gap larger than one is rejected in this slice so reconnect cannot silently skip unknown protocol work;
- a heartbeat for an obsolete generation, different Agent instance, wrong Backend or revoked credential fails closed;
- accepted heartbeats set `lastHeartbeatAt` and `leaseExpiresAt = acceptedAt + leaseDuration` using the Control-Plane clock;
- Agent timestamps are diagnostic only and never extend a lease.

The default contract uses a 30-second heartbeat interval, 90-second lease and 30-second stale grace. Concrete values are configuration with safe bounds, not wire authority.

### Derived state

Persisted lifecycle facts are combined with the Control-Plane clock:

- `revoked`: Agent binding or current runtime credential is revoked; no lease is valid;
- `incompatible`: last authenticated connect used no supported protocol version; no lease is valid;
- `online`: current generation has an unexpired lease and required read-only capability publication is valid;
- `stale`: lease expired but is within the bounded stale grace window;
- `offline`: no current lease, stale grace expired, no accepted instance exists or reconnect has not completed.

`stale` is a read-model state for this slice. It does not authorize live execution. Cached facts may remain visible with explicit staleness.

## Capability model

Capability publication is a small immutable set of facts for the current generation. Protocol and software version are persisted connection facts and remain separate from the capability revision. The published capability set contains:

- available local adapter kinds from the allowlist `suitebridge`, `restfulapi`, `svdrp`;
- `readOnly = true` (mandatory in this slice);
- supported observation domains from the allowlist `backend-health`, `channels`, `epg`, `recordings`, `timers`, `searchtimers`, `metadata`.

Capabilities contain no endpoint, URL, local path, process argument, environment value, credential, token, password, hash, cookie, CSRF value or Authorization header.

Capabilities are observations, not permission grants. Existing central authorization and backend access policy remain authoritative.

A capability publication:

- is bounded to 32 facts and 16 KiB encoded input;
- carries the current Backend, Agent instance and backend generation;
- advances `capabilityRevision` by exactly one when facts change;
- treats an exact duplicate as idempotent;
- rejects lower, skipped or cross-generation revisions;
- never renews a lease by itself.

## Connect and reconnect protocol

The first transport is narrow authenticated HTTP request/response over the existing daemon HTTP boundary. Production deployment requires protected transport at the reverse-proxy or daemon TLS boundary. The Agent initiates every request; no inbound VDR-site listener is required.

The protocol path is machine-only and rejects browser-session, Basic-user and CSRF credentials as Agent authentication. Runtime authentication resolves a persisted technical Agent credential through the existing security/credential repository; the protocol service receives only the resolved Agent actor and credential generation, never raw credential material.

Connection sequence:

1. authenticate technical Agent identity;
2. load Agent binding and existing BackendRegistry record;
3. reject unknown, revoked, expired or wrong-generation credential state;
4. validate request size, schema and protocol compatibility;
5. compare `AgentInstanceId` with the current accepted instance;
6. allocate or return `backendGeneration` transactionally;
7. return current heartbeat sequence, capability revision, lease policy and reconciliation disposition;
8. require capability publication and heartbeat before derived `online` state.

Reconnect dispositions:

- `resume`: same current instance and generation; continue from persisted sequences;
- `replace`: new accepted instance; increment generation and fence the previous instance;
- `resync-required`: claimed sequence or revision is ahead of persisted authority or cannot be reconciled;
- `rejected`: identity, binding, credential, revocation or protocol check failed.

No normal read path performs enrollment, credential creation, rotation or schema DDL.

### Credential rotation and recovery

An authenticated current Agent may rotate only its own persisted runtime credential. The request carries the bound Backend, current `AgentInstanceId`, current `backendGeneration`, current `CredentialGeneration`, a stable rotation ID and a newly generated secret. Central authorization grants only the narrow self-scoped `backend.agent.credential.rotate` action for the persisted Backend.

The verifier update, rotation record, credential-generation increment, lease invalidation and accountability result commit in one transaction. The old credential fails immediately after commit. Repeating the same rotation ID with the same next credential is idempotent; conflicting reuse, stale credential generation or obsolete Agent generation fails closed.

Before sending the request, the local Agent stores a 0600 pending-rotation recovery record. After an ambiguous transport result it first tests the pending credential, then either promotes it or reconnects with the old credential and resubmits the same rotation ID. It never guesses whether the server committed.

## Authentication and authorization boundaries

- Enrollment creation/approval is a protected Control-Plane transition requiring the existing central authorization decision and accountability precondition.
- Enrollment consumption authenticates only the one-time enrollment identity and may create only the pre-bound technical Agent identity.
- Runtime requests authenticate the resulting technical Agent actor and then enforce persisted Backend scope.
- Agent authentication never grants user permissions or global policy authority.
- Frontends and external clients cannot call Agent endpoints with normal sessions.
- Existing backend read-only policy remains an independent denial boundary.
- This slice has no Agent-triggered VDR operation, so no VDR mutation permission is introduced.

## Accountability contract

Required append-only events use the existing accountability repository and non-secret request/correlation context:

- `agent.enrollment.requested`;
- `agent.enrollment.succeeded`;
- `agent.enrollment.denied`;
- `agent.connection.accepted`;
- `agent.connection.denied`;
- `agent.generation.replaced`;
- `agent.lease.renewed` (rate-limited/no duplicate event for idempotent duplicate heartbeat);
- `agent.capabilities.published`;
- `agent.credential.rotation.requested`;
- `agent.credential.rotation.result`;
- `agent.revoked`.

Lease expiry is a deterministic clock-derived read state in this slice and does not create a speculative write or periodic transition event. A later explicit lifecycle projection may add an expiry event without changing lease authority.

Protected state changes fail closed when required pre-transition accountability cannot be persisted. Outcome events record success/failure without secret material.

## Redaction and secret rules

The following never enter normal logs, exceptions, HTTP bodies, accountability context, tests, fixtures, documentation or PR text:

- raw enrollment tokens;
- runtime credentials or private keys;
- password/token hashes or verifiers;
- cookies, CSRF values or Authorization headers;
- private provider credentials, URLs or local secret paths;
- secret-bearing process arguments or environment dumps.

Tests use opaque non-secret credential-reference identifiers and deterministic fake authenticators.

## Persistence and migration contract

Suite-owned SQLite tables are accessed only through repositories/services and are created by the existing migration/bootstrap path, never by normal reads.

The schema records:

- Agent identities and Backend binding;
- enrollment lifecycle and expiry;
- credential reference/generation, idempotent rotation history and revocation state;
- current Agent instance and backend generation per Backend;
- protocol/software version and compatibility result;
- heartbeat sequence, last connection/heartbeat and lease expiry;
- revocation reason and protocol-compatibility result;
- capability revision and normalized allowlisted facts.

Accountability request/correlation context is stored by the existing append-only accountability repository, not duplicated in Agent lifecycle tables.

Requirements:

- safe idempotent migration for existing installations;
- foreign keys to existing identity/Backend authorities where repository conventions permit;
- uniqueness preventing one Agent from binding multiple Backends and a partial unique index permitting at most one non-revoked Agent per Backend while retaining revoked history;
- transactionally allocated backend generations;
- restart persistence of current generation, sequences, capabilities and revocation;
- no destructive migration or automatic credential issuance during reads;
- schema/packaging/install-staging tests.

## Failure semantics

- database failure: fail closed; no in-memory-only enrollment, generation or lease authority;
- identity/security lookup failure: fail closed and emit only redacted error classification;
- accountability precondition failure: protected transition is not applied;
- incompatible protocol: no generation allocation and no lease;
- wrong Backend binding: deny without revealing another Backend's state;
- obsolete generation or instance: deny and do not renew lease;
- duplicate request: return the persisted result without duplicate transition;
- oversized or malformed input: reject before persistence;
- Control-Plane restart: rebuild status from persisted facts and current clock; expired leases do not become online;
- Agent disconnect: no immediate speculative mutation; lease naturally becomes stale then offline;
- reconnect with unverifiable sequence/revision: `resync-required`, never guessed continuity.

## Test gates

The slice is incomplete until observed tests cover domain validation, controlled/idempotent enrollment, invalid/expired/revoked enrollment, replacement enrollment after revocation, wrong Backend binding, incompatible protocol, generation replacement/fencing, monotone/duplicate/stale/gapped heartbeats, deterministic lease renewal/expiry, restart persistence, reconnect dispositions, capability allowlists/revisions/input limits, credential rotation/idempotency/fencing/lost-response recovery, redaction, accountability fail-closed behavior, backend isolation, unchanged direct-adapter online authority and absence of VDR writes.

The complete repository gates remain required: focused tests, architecture guards, fast regression, production daemon build, packaging/install staging, documentation checks and Make inventory audit. Real yaVDR acceptance must use the guarded [Phase 63 Backend Agent runtime acceptance runbook](phase-63-backend-agent-runtime-acceptance-runbook.md) to prove install/restart, enrollment/connect/capability/heartbeat, lease expiry, reconnect, rotation, revocation and replacement while confirming no VDR-native state changes.

## Real acceptance outline

1. install the exact candidate packages without exposing VDR provider ports;
2. create one controlled enrollment bound to one existing Backend;
3. start the Agent with protected local identity storage;
4. verify accepted protocol, generation and read-only capabilities;
5. verify persisted lease timestamps and the derived Agent `online` state without changing existing direct-adapter `BackendNode.online`;
6. stop the Agent and verify derived stale then offline state deterministically;
7. restart it and verify generation/reconciliation rules;
8. rotate the runtime credential and retain exact-head automated lost-response recovery evidence; deliberately dropping a committed HTTPS response is not required on the production yaVDR host;
9. revoke the Agent, prove reconnect/heartbeat denial and enroll a replacement while retaining revoked history;
10. verify Timer, Recording, SearchTimer, Remote, configuration and existing adapter availability state are unchanged;
11. retain only redacted logs and exact-head evidence.

## Rollback

Stopping/removing the Agent runtime leaves existing local Backend adapters and cached Suite data intact. The guarded runtime harness removes test-created Agent identities and restores the previous Agent configuration on failed acceptance so a bounded retry does not require manual SQLite surgery. Rolling back the daemon must not expose secrets; additive tables may remain unused. Any future destructive schema cleanup requires a separate migration. Revocation remains the immediate operational containment action.
